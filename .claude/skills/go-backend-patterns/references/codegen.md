## Detect what the project generates

Check before writing code by hand. Writing a handler, DTO or query that a generator owns
produces code the next `go generate` silently overwrites or contradicts.

| Signal in the repo | Generator | Then |
|---|---|---|
| `oapi-codegen.yaml` or `*.cfg.yaml` with `generate:`, `//go:generate ... oapi-codegen`, files headed `Code generated by ... oapi-codegen` | oapi-codegen | edit the OpenAPI document, regenerate, implement the strict interface (openapi-strict.md) |
| `sqlc.yaml` or `sqlc.json` | sqlc | write SQL in the queries folder, regenerate, call the generated `Queries` from the repository |
| `// @Summary` comments on handlers, `docs/swagger.*` | swag | update the comments, run `swag init` |
| `buf.yaml`, `buf.gen.yaml`, `*.pb.go` | buf or protoc | edit the `.proto`, regenerate (grpc.md) |
| `.mockery.yaml`, `//go:generate mockgen` | mockery or mockgen | regenerate mocks after changing an interface. New tests may still use hand-written fakes (testing.md) |
| `wire.go` with `//go:build wireinject` | wire | add the provider to the wire set instead of editing the container by hand |

`grep -rn "go:generate" --include=*.go .` and `grep -rln "Code generated" --include=*.go .`
find most of them in one pass.

## Rules for every generator

1. **Never edit a generated file.** Files starting with `// Code generated ... DO NOT EDIT.`
   are rewritten on the next run. Change the source (spec, SQL, proto, comments) instead.
2. **Regenerate in the same change** as the source edit: `go generate ./...` (or the project's
   `make generate`). A spec change without regenerated code breaks the build for the next person.
3. **Commit generated code** unless the project's `AGENTS.md` says otherwise. Reviewers then see
   what the change does to the API, and builds need no generator installed.
4. **CI proves it is fresh:** `go generate ./... && git diff --exit-code` fails when someone
   edited the source but not the output, or the reverse.
5. **Hand-written code wraps generated code, never the other way.** The module's handler
   implements the generated interface, and the repository calls the generated queries. Business
   logic stays in the service, which knows nothing about either generator.

## Pinning generator versions with `go tool`

Go 1.24 added `tool` directives to `go.mod`, so generator versions are pinned like any other
dependency and every machine runs the same version:

```bash
go get -tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@v2.8.0
go get -tool github.com/sqlc-dev/sqlc/cmd/sqlc@latest
```

```go
//go:generate go tool oapi-codegen -config oapi-codegen.yaml ../../api/openapi.yaml
```

On a `go` directive older than 1.24, the project uses a `tools.go` file with blank imports
instead. Follow whichever the project already has.

## Where generated code goes in a module-first layout

Generated code is the one exception to "one package per module, no sub-packages":

| Generated | Location | Imported by |
|---|---|---|
| OpenAPI types and strict interface for the whole API | `internal/api/gen/` (leaf package) | the modules' strict handlers and `internal/api` |
| sqlc queries for one module | `internal/<module>/<module>db/` (for example `internal/order/orderdb/`) | that module's repository only |
| protobuf | `<org>/shared/proto/...` or `proto/gen/` | gRPC adapters and clients |

Generated sub-packages are fine because nobody writes code in them. `check_boundaries.sh`
already rejects another module importing `internal/order/orderdb`, so a module's generated
queries stay private to it like its repository.

## oapi-codegen

A config file next to the generate directive, for Gin with the strict server:

```yaml
# internal/api/gen/oapi-codegen.yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/oapi-codegen/oapi-codegen/v2.8.0/configuration-schema.json
package: gen
generate:
  gin-server: true
  strict-server: true   # needs another server generator next to it (gin-server here)
  models: true
  embedded-spec: true   # lets a request validator middleware read the spec at runtime
output: api.gen.go
```

```go
// internal/api/gen/generate.go
package gen

//go:generate go tool oapi-codegen -config oapi-codegen.yaml ../../../api/openapi.yaml
```

- The OpenAPI document lives at the repo root (`api/openapi.yaml`). Tag each operation with
  its module (`tags: [orders]`) so ownership is visible in the spec too.
- `output-options.include-tags` generates only the operations of some tags. Use it to split a
  very large spec into one generated package per module, at the price of duplicated shared
  schemas across those packages.
- Implementing and wiring the strict handlers per module: openapi-strict.md.

## sqlc

sqlc turns SQL files into typed Go. In module-first, each module gets its own `sql` entry, so
its generated package is private and its queries sit next to it:

```yaml
# sqlc.yaml
version: "2"
sql:
  - engine: postgresql
    schema: migrations
    queries: internal/order/queries
    gen:
      go:
        package: orderdb
        out: internal/order/orderdb
        sql_package: pgx/v5
```

The module's repository wraps the generated `orderdb.Queries`, maps rows to the module's model,
and turns `pgx.ErrNoRows` into the module's `ErrNotFound`. The service still sees only the
`repository` interface, so switching between GORM, go-pg and sqlc never reaches the service.

## swag, protobuf, mocks

- **swag**: comments on each handler method (handler.md), regenerate with
  `go tool swag init -g cmd/api/main.go -o docs`. With oapi-codegen the spec is the source and
  swag is not used.
- **protobuf**: `buf generate` (or the project's `protoc` command) after editing `.proto` files.
  Breaking changes (renumbered or removed fields) need a new package version (`v2`).
- **mocks**: when the project generates mocks, regenerate them after changing an interface. For
  the small interfaces in this skill (`repository`, `transactor`, readers of other modules), a
  hand-written fake is usually shorter than the generated mock and behaves like the real thing.
